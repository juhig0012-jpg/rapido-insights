# Rapido: Intelligent Mobility Insights

Ride pattern analysis, cancellation/delay risk prediction, and fare
forecasting for a ride-hailing platform, built as an end-to-end pipeline:
data cleaning → feature engineering → four trained models → a SQL
database → an EDA report → an interactive Streamlit dashboard.

## What this project does

Given a booking's details (pickup/drop, vehicle type, time, traffic,
weather), predicts whether the ride will complete, cancel, or go
incomplete; estimates the fare before the trip starts; and scores how
likely the customer is to cancel or the driver is to run late - all from
four separately-trained models you can query interactively. The dashboard
also answers the "what's actually going on" questions (peak hours, which
cities cancel more, which vehicle types are most reliable) without writing
any code or SQL yourself.

## A note on the dataset

This project ships two very different raw datasets, and only one of them
is actually usable for the models the spec asks for:

- **`data/raw/rides_data.csv`** - ~50,000 real ride records, but with no
  `customer_id`/`driver_id`, no traffic/weather/surge columns, and a
  different fare breakdown (`ride_charge` + `misc_charge` = `total_fare`).
  It's large, but it can't support three of the four required models -
  there's no way to compute a customer's historical cancellation rate or a
  driver's delay history without a customer/driver identifier.
- **The bookings/customers/drivers/location_demand/time_features tables**
  (what everything below actually uses) - originally shipped as a
  15-booking hand-written sample with exactly the columns every model
  needs (fare, surge, traffic, weather, driver delay, cancellation
  reason), but far too small to train anything meaningfully or trust a
  reported accuracy number on.

`src/generate_synthetic_data.py` regenerates that second dataset at a
realistic scale (6,000 bookings, 400 customers, 150 drivers) in the exact
same schema, with cancellation/delay probabilities that actually depend on
the customer's/driver's history and the trip's traffic/weather - so the
models have real signal to learn and the accuracy/RMSE numbers in
`reports/MODEL_EVALUATION.md` mean something. `rides_data.csv` is left in
`data/raw/` but unused; nothing in the pipeline reads it.

## Objectives

- Predict ride outcome (Completed / Cancelled / Incomplete)
- Predict the expected fare before a trip starts
- Score customer cancellation risk and driver delay risk
- Explore ride patterns, cancellations, and fares through a written EDA
  report and an interactive dashboard
- Store the cleaned data in a real, queryable SQL database

## Running the Pipeline

Run these from the project root, in order:

```bash
# 1. (Optional) regenerate the raw CSVs at a larger, realistic scale
python src/generate_synthetic_data.py

# 2. Clean the raw data
python src/data_cleaning.py

# 3. Merge tables and engineer features
python src/feature_engineering.py

# 4. Train all four models + write reports/model_metrics.json and MODEL_EVALUATION.md
python src/train_model.py

# 5. Generate the EDA charts + written report
python src/eda.py

# 6. Load the cleaned data into a local SQLite database
python src/load_db.py

# 7. Launch the dashboard
streamlit run app/streamlit_app.py
```

Step 1 is optional if you already have raw CSVs in `data/raw/` in the same
schema - skip straight to step 2. Steps 2-6 can be run independently of
each other in any order *after* their own prerequisites are met (EDA only
needs step 3's output; the database load only needs step 2's output).

The dashboard opens at `http://localhost:8501`.

## Models

| Model | Type | File |
|---|---|---|
| Ride Outcome | Multiclass classification (RandomForest) | `models/ride_outcome_model.pkl` |
| Fare Prediction | Regression (XGBoost) | `models/fare_model.pkl` |
| Customer Cancellation Risk | Binary classification (RandomForest) | `models/customer_cancel_model.pkl` |
| Driver Delay Risk | Binary classification (RandomForest) | `models/driver_delay_model.pkl` |

Every model is tuned with a small `GridSearchCV` sweep (see
`src/train_model.py`) rather than fixed hyperparameters, and every model's
test-set metrics are written to `reports/model_metrics.json` and
`reports/MODEL_EVALUATION.md` so they're checkable later rather than only
ever appearing once in a terminal.

### Benchmark results (target: 85-90% classification accuracy, RMSE within ±10% of mean fare)

| Model | Result | vs. benchmark |
|---|---|---|
| Ride Outcome | 65.8% accuracy, AUC 0.60 | Below target |
| Fare Prediction | RMSE 5.8% of mean fare, R²=0.99 | Meets target |
| Customer Cancellation Risk | 82.5% accuracy, AUC 0.61 | Below target |
| Driver Delay Risk | 92.6% accuracy, AUC 0.83 | Meets target |

Fare prediction and driver delay risk clear the target. Ride outcome and
customer cancellation risk don't - and honestly, that tracks: both are
predicting an inherently noisy human decision (whether *this specific*
booking gets cancelled) from aggregate historical signals, and the
majority-class baseline (always guessing "Completed" / "No Cancel") already
sits at 69%/83% - so there's real, if modest, lift over that baseline, just
not enough to hit an 85-90% target on tasks this noisy. Re-run
`python src/train_model.py` any time the underlying data changes to refresh
these numbers.

## SQL Database

`db/schema.sql` defines a normalized schema - `customers`, `drivers`,
`location_demand`, and `time_features` as dimension tables, `bookings` as
the fact table referencing all four by foreign key, plus indexes on the
columns the dashboard and EDA actually filter/group by (customer_id,
driver_id, city, ride_status, booking_time).

`src/load_db.py` applies that schema to a local SQLite file
(`db/rapido.db`) and loads the cleaned CSVs into it - SQLite specifically so
running this doesn't require installing or configuring a database server;
the DDL itself is plain enough to run on Postgres/MySQL with minor type
changes if this ever needs a real server.

`db/analysis_queries.sql` has ready-to-run queries for the EDA-style
questions (cancellation rate by city, by traffic level, by weather;
payment method usage; top drivers by delay; top customers by cancellation
rate). Run them with any SQLite client, or from Python:

```python
import sqlite3
conn = sqlite3.connect("db/rapido.db")
for row in conn.execute("SELECT city, COUNT(*) FROM bookings GROUP BY city"):
    print(row)
```

## EDA

`src/eda.py` answers the seven EDA questions from the project spec - ride
volume by hour/weekday/city, a cancellation-rate heatmap across cities and
time-of-day, distance-vs-fare correlation, rating distributions, a
customer-vs-driver cancellation comparison, payment method usage, and
traffic/weather vs cancellation rate. It writes `reports/EDA_REPORT.md`
with the actual numbers and saves every chart to `reports/eda_charts/`.

`notebooks/EDA.ipynb` predates this script and isn't actually a valid
notebook (it's plain Python text saved with a `.ipynb` extension - it won't
open in Jupyter). It's safe to delete; `src/eda.py` is the real EDA
deliverable.

## Demo Walkthrough

After running the full pipeline, `python src/predict.py` runs all four
models against a real row from the processed dataset as a sanity check:

```
Ride outcome: Completed
Fare: 62.36
Customer cancel risk: (0, 0.1033)
Driver delay risk: (0, 0.13)
```

In the dashboard itself: open the **Dashboard** page for headline metrics
and a live read of `reports/model_metrics.json`; **EDA** for a quick
city-filtered look at the data (the full write-up is in
`reports/EDA_REPORT.md`); and the four prediction pages to try a booking
against each model interactively - each one starts from a real booking as
a template and only asks you to change the handful of fields relevant to
that prediction, so you don't have to fill in all ~50 columns by hand.

## Troubleshooting

| Problem | Solution |
|---|---|
| `streamlit` command not found | Use `python -m streamlit run app/streamlit_app.py` |
| `FileNotFoundError` for a processed/ CSV or a model .pkl | Run the missing earlier pipeline step (see Running the Pipeline above) |
| `ModuleNotFoundError` | `pip install -r requirements.txt` |
| Dashboard prediction pages error out | Make sure `train_model.py` was re-run after the most recent `feature_engineering.py` run, so the models match the current column set |
